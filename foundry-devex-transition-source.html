03 · Extension evolution

From two extensions to one Foundry Toolkit.

The current Toolkit brings the former AI Toolkit and Microsoft Foundry extension capabilities together in one VS Code extension.

How consolidation happened

  • May 2024 — AI Toolkit reached general availability.
  • March 2025 — The separate Azure AI Foundry extension reached general availability.
  • April 16, 2026 — AI Toolkit became Microsoft Foundry Toolkit for VS Code v1.0.
  • May–August 2026 — The former Microsoft Foundry extension capabilities moved into the Toolkit. Microsoft Learn documented the consolidated extension by August 25.

04 · VS Code surface

Why the editor experience is distinct.

Foundry Toolkit keeps agent work close to the repository, development environment, and GitHub Copilot.

  • Work where the code lives — Build against the project and repository context already open in VS Code.
  • Use an integrated AI workflow — Connect GitHub Copilot, models, agents, and developer tools without switching to a separate browser workflow.
  • Inspect behavior while building — Use Agent Inspector to review runs, tool calls, traces, and intermediate outputs.
  • Continue through the lifecycle — Prototype, test, debug, evaluate, and deploy from the development environment.
05 · Developer surfaces

One platform, three ways to work.

The surfaces overlap. The right starting point depends on whether the work is visual, repository-centered, or automated.

Visual

Foundry portal

Use the browser to explore models, configure and test agents, review deployed behavior, and work with broader administration and governance.

Integrated

Foundry Toolkit for VS Code

Use the editor and repository context to build, debug, test, evaluate, and iteratively deploy.

Automated

Foundry CLI / azd ai

Use terminal-first commands for repeatable workflows, scripts, and CI/CD automation.

06 · Reach & adoption

What the latest signals tell us.

The available evidence shows broad Marketplace reach and part of the journey from creating an agent to inspecting how it runs.

Marketplace reach · Sep 11

1,391,574 installs

A cumulative distribution signal—not active users or retention.

Agent creation · Jul 11–Aug 7

~1,100 devices

Successfully scaffolded an agent during the reporting window.

Agent Inspector · Jul 11–Aug 7

~29% attempted

About 26% connected successfully; about 71% did not attempt Inspector.

How to read the product impact

  • The extension has broad reach — The Marketplace count shows how widely the Toolkit has been distributed, but not how often people use it.
  • Agent creation is happening inside VS Code — The scaffolding count is the clearest recent product-specific signal of people beginning the agent-development journey.
  • Inspection is not yet a default next step — Most devices that scaffolded an agent did not attempt Agent Inspector during the same reporting window.
  • Agent Builder resonates in research — In a small May study, all seven participants quickly chose “Design an Agent without Code.” Treat this as qualitative feedback, not an adoption percentage.

11 · VS Code UI system

One shared layer between Fluent and VS Code.

vsc-ui-react prevents every feature from rebuilding the same styling and interaction decisions.

VscButton · VscInput · VscTabListReusable wrappers and documented patterns
Fluent UIBehavior, interaction states, and accessibility
VS Code tokensTheme, density, spacing, and visual language
StorybookReference implementation
FigmaDesign specifications
Why it startedThe retired Webview UI Toolkit left teams creating local Fluent overrides.
What it providesShared npm components, tokens, states, documentation, and examples.
Current caveatSubstantially implemented; complete legacy migration is not proven.

New designer contribution checklist
  1. Start with Figma and Storybook; reuse an existing component when possible.
  2. For gaps, map Fluent behavior to VS Code conventions and CSS tokens.
  3. Validate light, dark, and high-contrast states.
  4. Update Storybook and Figma, then request design and engineering review.
  5. Migrate production callsites through a separate Skylight PR when appropriate.
